# 黄灯修复手册

只处理**用例缺陷**（黄灯）。红灯交人工，灰灯不修，flaky 只隔离。

## 前置：修之前先确认三件事

1. **spec 里到底怎么写的**——打开 OpenAPI 确认字段的 `required`、`type`、`enum`、`minimum`/`maximum`。用例错还是实现错，这一查就知道。
2. **是不是环境问题**——同接口别的状态码用例过了吗？别的接口正常吗？批量失败先怀疑环境（回灰灯）。
3. **是不是契约漂移**——源码里根本没有这个校验，或者字段名对不上。这种按铁律 5 登记漂移，**不许自行改断言站队**。

## 按症状修

### 症状：期望 400，实际 200

```
1. 查 spec：该字段是否在 required 列表？
   ├─ 在 → 这是实现缺陷，转红灯，不要改断言
   └─ 不在 → 用例写错了
2. 用例错的话：把这条用例从"校验类"改成"可选字段类"，
   期望改为 200，并补一条 json_path 断言确认该字段被正确置为默认值
```

**注意**：改成 200 不是降级，是纠正分类。但要补上默认值断言，保证强度不净降。

### 症状：响应字段缺失

```
1. 字段名拼错？对照 spec 的 response schema 逐字母比对（大小写、下划线）
2. 字段在嵌套层里？确认 json_path 写对（$.data.items[0].id）
3. 该字段只在特定条件下返回？补一条条件化用例，而不是删断言
```

### 症状：前置数据不存在 / 404

```
1. setup 步骤有没有执行成功？看 execution_results.json 的 setup 明细
2. setup 建了但 ID 没传进请求？检查 {{var}} 占位符是否拼对
3. 数据被别人删了（共享环境）？加唯一前缀 autotest_{{run_id}}_ 并自带 setup
```

### 症状：schema 校验失败

```
1. schema_ref 指错了？对照 spec 里的 components/schemas 名字
2. 响应多了字段 → 记契约漂移，不要用 additionalProperties 一把放过
3. 响应少了字段 → 大概率红灯（实现缺陷），不要改 schema_ref 绕开
```

### 症状：401

```
1. 用例漏带 Authorization 头 → 补上（token 走环境变量，禁止写死）
2. 全部用例都 401 → 灰灯，token 过期，回 Step 0
3. 单条 401 → 检查这条用例是不是故意测无 token 场景但期望值写错了
```

### 症状：数据冲突 / 唯一键重复

```
1. 资源名没带唯一前缀 → 加 autotest_{{run_id}}_
2. teardown 没清干净 → 检查 teardown 是否执行，失败了要在报告里登记残留
3. 用了别人的固定 ID → 改成自建数据
```

## 修复的硬性要求

- **只改用例文件**（`cases.json`），不许碰被测服务代码
- **局部 diff**，不整文件重写
- **断言强度只增不减**：删掉一条强断言必须补一条等价强度的
- 每处修改在报告里留 diff，写清"改了什么、为什么"

## 改完之后

```bash
python scripts/run_cases.py --cases workspace/cases.json --out workspace/execution_results.json
```

复跑后检查两件事：
1. 目标用例变绿了吗？
2. **有没有引入回归**？原来绿的其他用例是否还绿？

有回归 → 立即停止，升级人工（铁律 3）。

## 修不动的时候

同一处修 3 次还失败 → 停下来质疑**接口设计本身**：
契约是不是自相矛盾？字段语义是不是本来就模糊？是不是该改 spec 而不是改用例？
把这个问题抛给人工，不要第 4 次尝试。
