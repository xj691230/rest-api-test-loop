# 反模式与常见自我合理化

抄 `obra/superpowers` 的体例：把"听起来合理其实是偷懒"的念头提前点破，因为它们在跑的当下都很有说服力。

## 断言降级类（违反铁律 2）

| 内心独白 | 为什么是错的 |
|---|---|
| "这个字段实现里没有，把断言删了吧" | 字段缺失是**发现**，不是噪音。删掉就永远发现不了了。正确做法：记红灯或契约漂移 |
| "有的环境返回 400 有的返回 200，改成 in [400,200] 吧" | 这正是被掩盖的不一致。改成 `in` 之后这条用例等于不存在 |
| "精确值太脆了，改成 not_empty 就行" | 断言强度从强降到弱，必须补别的强断言补偿，不能净降 |
| "schema 校验总失败，先去掉，后面再补" | "后面再补"永远不发生。schema 断言是最有价值的契约守卫 |
| "时间不够，这几条先 skip" | skip 的用例不会有人回来补。要么跑要么不生成 |

**自检**：本轮结束后，能拿出断言强度的 diff 吗？拿不出来就是没守住。

## 环境归因类

| 内心独白 | 为什么是错的 |
|---|---|
| "肯定是环境抖了，重跑几次就好" | blanket retry 掩盖真实失败。flaky 判别（重跑 ×3）才是正规途径，且 1~2/3 通过的要**隔离不修** |
| "加个 sleep(3) 应该就稳了" | 无脑 sleep 不治根因，还拖慢全套件。真有时序依赖就显式等待条件成立 |
| "测试环境太脏了，用例改宽松点" | 脏数据是共享环境的现实，正解是**唯一前缀 + 自带 setup**，不是放宽断言 |
| "连不上，可能是服务在重启，等等再跑" | 可以等，但要回 Step 0 做健康检查确认，不能凭感觉 |

## 越权类（违反修复边界）

| 内心独白 | 为什么是错的 |
|---|---|
| "被测代码就改一行，我直接改了效率更高" | 产品代码改动必须人工确认，这是本 skill 的安全底线。改一行也可能引发编译失败或回归 |
| "OpenAPI 明显过时了，我按实现更新 spec" | 违反铁律 5。契约漂移的裁决权在人手里，agent 只负责把冲突摆出来 |
| "我把整个用例文件重写一遍更干净" | 只接受局部 diff。整文件重写无法审计，也容易顺手改掉断言 |
| "先改了再说，反正是开发环境" | 开发环境的代码同样要进主干。边界不因环境而变 |

## 循环失控类（违反铁律 3）

| 内心独白 | 为什么是错的 |
|---|---|
| "再跑一轮肯定能过" | 3 轮封顶。连续两轮无新增修复就说明方向错了，继续只是烧时间 |
| "这个修复引入了一个新失败，先修新的再说" | 出现回归立即停止升级人工。边修边炸的循环没有收敛性 |
| "只剩两条失败了，值得再跑一轮" | 剩余数量不决定是否继续，收敛趋势才决定。连续两轮无新增修复就停 |

## 用例质量类

| 反模式 | 正解 |
|---|---|
| 一条用例塞 10 个断言，失败时看不出哪个错 | 按行为拆分，一条用例一个关注点 |
| 依赖执行顺序（先创建再查询，分两条用例） | 每条自带 setup，可独立运行 |
| 用真实业务数据（别人的订单 ID） | 一律自建带 `autotest_` 前缀的数据 |
| 造了数据不清理 | 必须 teardown，失败也要登记残留 |
| 断言只查 status code | 至少补 schema 和关键字段断言，只查状态码等于没测业务 |
| 一次生成 200 条再跑 | 分批（P0 → P1 → P2），早发现共性问题 |
