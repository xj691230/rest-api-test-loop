# 失败归因决策树

只处理 Step 5 判为 **0/3 确定性失败**的用例。每个失败打**且仅打一个**标签。

## 快速分流（按顺序判断，命中即停）

```
失败用例
 ├─ 服务连不上 / 超时 / 批量 401 / 429        → 灰灯 · 环境噪声
 ├─ 契约没规定，是用例自己的假设              → 黄灯 · 用例缺陷
 ├─ 契约明确要求，实现不符                    → 红灯 · 产品缺陷
 └─ 判断不清                                  → 黄灯（默认先怀疑自己的用例）+ needs_review
```

## 灰灯 · 环境噪声（不修，重试 2 次，仍失败则挂起报障）

| 信号 | 可能原因 | 处置 |
|---|---|---|
| `Connection refused` / DNS 失败 | 服务没起、URL 错 | 回 Step 0 重做健康检查 |
| **所有**用例 401 | token 过期或格式错 | 刷新 token，检查 Authorization 头格式与 scope |
| 429 | 限流 | 降低并发、串行跑、加间隔（**不是加 retry 掩盖**） |
| 超时 | 服务卡住 / 在重启 / 依赖的下游挂了 | 开发环境可重启后重试；共享环境找人确认 |
| 5xx 且伴随服务重启日志 | 部署中 | 等部署完成后复跑 |

**判据**：环境噪声通常是**批量的、跨接口的**。单个接口失败而别的接口正常，基本不是环境问题。

## 黄灯 · 用例缺陷（自动修，只改用例，不改被测代码）

| 信号 | 根因 | 修法（见 repair-playbook.md） |
|---|---|---|
| 期望 400 实际 200 | 断言写错，或该字段其实非必填 | 先查 spec 的 required；spec 没标 → 改断言；spec 标了 → 转红灯 |
| 响应字段缺失 | 用了 spec 外的字段名 | 按 spec 改字段名 |
| 前置数据不存在 | setup 没建 / 建失败 | 补 setup 或修正依赖 |
| 数据被别人改了 | 共享环境脏数据 | 加唯一前缀 + 自带 setup |
| schema 校验失败但字段是对的 | 断言的 schema 引用错了 | 修正 `schema_ref` |
| 401 | 用例漏带 token | 补 auth |

## 红灯 · 产品缺陷（不自动改，定位到 file:line 后交人工）

| 信号 | 说明 |
|---|---|
| spec 标 required，缺失该字段却返回 200 | 校验缺失 |
| 应 400 却 500 | 异常未捕获 |
| 响应 schema 字段缺失或类型错 | 结构体与 spec 不符 |
| 应 404 却 200 返回空 | 资源不存在未正确处理 |
| 应 403 却 200 | 越权校验缺失 |

**归因完成的标志**：给出 `file:line` + 一句话说明"契约要求 X，源码第 N 行只做了 Y"。
只说"接口返回不对"= 归因未完成，不许进 Step 7。

### 用源码定位（有代码仓的优势在这里兑现）

按 `references/source-mapping.md` 定位 handler 后：

1. 找到该接口的 handler 函数 → 记 `file:line`
2. 读参数解析与校验段 → 确认是否缺校验
3. Grep 错误码常量 → 确认返回码是否符合 spec
4. 找响应 `struct` → 对照 spec 的 response schema

产出格式：

```
红灯 · 产品缺陷
接口：POST /api/v1/orders
契约要求：price 为必填，缺失应返回 400 + code=INVALID_PARAM
实际：返回 200
定位：src/handler/order_handler.cc:142 —— createOrder() 直接调用 getOptional("price")，未做必填校验
建议：改为 getRequired 或在 142 行前加空值判断
影响用例：POST /api/v1/orders__missing_price
```

## 契约漂移（不算失败，单独登记）

OpenAPI 与源码不一致时**不许自行选边**（铁律 5）。登记到 `contract_drift.json`，报告里单列一章交人工裁决。

| 冲突 | 处置 |
|---|---|
| spec 有 required，源码无校验 | 可能是实现缺陷，也可能是 spec 过期 → 交人工 |
| spec 无 required，源码有校验 | 记漂移，用例按 spec 写；红灯时优先怀疑 spec 过期 |
| 枚举范围不一致 | 边界用例取并集，冲突记漂移 |
| spec 有路由，源码无 | 死文档，记漂移，不生成用例 |
| 源码有路由，spec 无 | 未文档化接口，补冒烟用例并登记 |

## 反复失败的处置

同一处修复失败 **3 次** → 停止，质疑接口设计本身（抄 `systematic-debugging`）：
契约是否自相矛盾？字段语义是否本身就模糊？是不是该改 spec 而不是改代码？
把这个问题抛给人工，不要第 4 次尝试。
