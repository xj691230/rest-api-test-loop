# REST 接口测试闭环 Skill 设计（v0.3 设计稿）

- **被测对象**：任意语言实现的后台 REST 接口（黑盒 HTTP 测试，不改动、不编译被测代码）
- **基线**：`rest-api-test-loop` v0.2.0 —— 9 步闭环、5 条铁律、失败三分类（产品缺陷/用例缺陷/环境噪声+flaky）、契约×源码交叉验证
- **本稿核心增量**：**测试数据供给子系统（Data Provisioning）** —— 解决"用户怎么方便地提供用例数据（不同资源类型等）"的问题
- **性质**：面向商业级交付质量要求，设计需可落地为 skill 的脚本与参考资料

---

## 0. 先回答核心问题：测试数据怎么让用户方便地提供？

常见的直觉——"用例聚合之后让用户一次性提供"——**方向是对的，但直接这么做会踩两个坑**：

1. **如果什么都问用户，清单会爆炸。** 一轮闭环动辄上百条用例，逐条问数据等于把测试设计的负担又扔回给用户；
2. **闭环是迭代的，没有真正意义的"一次性"。** 修复轮次会新增数据需求，纯一次性清单要么缺数据卡死，要么反复打扰用户。

所以正确的设计是三句话：

> **先分流，再聚合；聚合的是"语义需求"而不是"具体数据"；迭代时做增量 diff，不重问。**

具体机制（详见 §4）：

1. **先分流**：数据需求分三层。凡是**被测系统自己的接口能创建的资源**（大多数资源对象、业务配置），由闭环 setup 阶段自动创建、teardown 自动清理——**这部分根本不需要用户提供**（参考 RESTler 的 producer-consumer 依赖）。只有"接口造不出来"的资源才流向用户；
2. **聚合语义需求**：用例只声明 `needs`（如"需要一个 device 类型的资源，任意厂商"），不写具体值。所有用例生成完毕后，聚合器把全部 needs **去重归并**成一份填空式 YAML 清单（data-manifest.yaml）。200 条用例的数据需求去重后，通常只剩**个位数的填空项**——这才是用户"一次性提供"的正确粒度；
3. **增量 diff**：第 2、3 轮修复产生的新需求，只把新增项追加到 manifest 尾部并标记 `delta`，已填部分原封不动。用户每轮最多看新增的几行。

一句话总结：**用户面对的不是 200 条用例的数据，而是去重后的资源需求清单；且其中大部分已经被自动层消化掉了。**

## 1. 基线评估：v0.2 已经做对了什么（保留项）

| v0.2 机制 | 保留理由 |
|---|---|
| 黑盒 HTTP 用例 + Python 执行器 | 被测侧零编译，秒级反馈，这是闭环可行性的根基 |
| 契约 × 源码交叉验证 + 漂移登记 | 商业级核心增值：spec 是意图、源码是事实，冲突交人裁决 |
| 失败三分类（红/黄/灰）+ flaky 判别（0/3、1-2/3、3/3） | 防止"把环境抖动当 bug 修"，分类先于修复的铁律业界少有，保留 |
| 3 轮上限 + 断言强度只增不减 | 防闭环空转、防放宽断言换绿灯 |
| setup/teardown + `autotest_<runid>_` 唯一前缀 | 数据残留防护，保留并升级为 §4 的自建层机制 |

**缺口**：v0.2 只有"每条用例自带 setup/teardown"这一个数据机制，没有体系化的数据供给设计。用例之间会重复造同样的资源、无法引用环境里已有的真实/模拟设备、更没有给用户的聚合供给通道。§4 即为此而设。

## 2. 业界实践调研 → 设计决策映射

调研对象：学术工具（RESTler、Schemathesis、EvoMaster、RestTestGen、Morest、RestCT、RESTest，含两篇系统性综述）+ 工业框架（Karate、Dredd、字节 BAM/美团 Lego 的平台化思路）。

| # | 业界实践 | 来源 | 采纳方式 |
|---|---|---|---|
| 1 | **契约 examples 优先取值**：spec 内的 example/default/enum 比随机值能触发更多真实行为 | Schemathesis（实测覆盖率仅次于 EvoMaster 白盒） | 用例生成取值优先级定为：`spec example > enum/default > 业务字典 > 规则构造`。副作用：数据需求天然变少 |
| 2 | **生产者-消费者依赖**：POST 返回的 id 喂给后续 GET/PUT/DELETE，自动串成合法调用链 | RESTler、RestTestGen（ODG）、Morest（属性图） | 升级 v0.2 的 setup/capture 机制成 §4 的 L1 自建层：needs 声明 → resolver 自动展开为"创建→捕获→注入→清理"链 |
| 3 | **用户值字典**：`custom_values.json` 让用户提供特定字段的领域值 | EvoMaster | 对应 data-manifest.yaml 的 `values` 段（字段级领域值，如设备型号枚举） |
| 4 | **数据与用例分离**：测试数据放 CSV/JSON/YAML 外部文件，运行期读取；@setup 标签统一造数 | Karate | 对应 §4 的 manifest 外置 + 资产池外置；用例文件里永远只有 `needs` 引用 |
| 5 | **状态属性即免费用例**：如"GET 在 DELETE 之后应 404""重复 POST 应 409"这类语义属性 | Schemathesis | 纳入用例矩阵（case-matrix.md 新增 `property` 类别），不增加数据需求却能加断言密度 |
| 6 | **失败序列黑名单**：执行中 500 的调用序列记黑名单，后续不再生成 | RESTler | 归因环节产出"环境特性知识"（如某接口偶发 429），下轮自动避开或降并发 |
| 7 | **黑盒为主 + 源码做裁决**：纯黑盒覆盖有瓶颈时用白盒信息引导 | 学术综述共识；v0.2 已采用 | 维持：黑盒跑用例、源码仓只用于交叉验证与红灯定位 file:line |
| 8 | **平台化一站式（任务构建→执行→校验→报告）** | 字节 BAM、美团 Lego | skill 本身就是这条流水线的 agent 化形态，无需引入平台依赖 |

**不采纳的**：EvoMaster 的进化算法生成（黑盒场景下对强业务约束的领域系统取值命中率低，且不可解释、不可审阅——商业级用例要能给人看）；Dredd 的哑值模式（无法触达边界行为）。

## 3. 总体架构 v0.3

```
┌─ 契约层 ──────────────────────────────────────────────┐
│ Step 1 解析 OpenAPI → endpoints.json                   │
│ Step 2 契约×源码交叉验证 → contract_drift.json          │
├─ 用例层 ──────────────────────────────────────────────┤
│ Step 3 按矩阵生成用例 → cases.json（只含 needs 声明）    │
├─ 数据层（新增，§4）────────────────────────────────────┤
│ Step 3.5 数据装配：聚合 needs → 三层分流 → manifest     │
│         → 用户填空（仅 L3）→ resolve → cases.resolved   │
├─ 执行层 ──────────────────────────────────────────────┤
│ Step 4 执行（含 L1 自动造数 + teardown 清理）           │
├─ 归因修复层 ──────────────────────────────────────────┤
│ Step 5 flaky 判别 → Step 6 归因三分类 → Step 7 修复     │
│ Step 8 复跑（≤3 轮）→ Step 9 报告                       │
└───────────────────────────────────────────────────────┘
```

数据层是唯一的大改动：在"生成"和"执行"之间插入 **Step 3.5 数据装配**，执行器读的是 resolve 之后的 `cases.resolved.json`，其余步骤对 v0.2 完全兼容。

## 4. 测试数据供给子系统（本稿核心）

### 4.1 设计原则：用例与数据解耦

用例文件里**永远不写具体环境数据**（资源 ID、实例 IP、license 路径），只写语义化的 `needs` 声明。数据在两个外部文件里维护：`data-manifest.yaml`（本轮运行的用户输入）和 `environment.yaml`（长期资产池）。带来的商业级收益：

- **环境可迁移**：换环境只改 manifest/池，用例资产零改动，回归直接复用；
- **可审阅**：用例评审时看到的是意图（"需要一个 OTN 类型设备"），不是脆弱的具体值；
- **闭环可迭代**：需求变化走增量 diff，不污染已验证的用例。

### 4.2 三层分流模型

每个 `need` 由聚合器判定归入哪一层，判定顺序固定：

| 层 | 判定条件 | 供给方式 | 用户负担 |
|---|---|---|---|
| **L1 自动自建** | 被测系统存在能创建该资源的接口（从 endpoints.json 里找 POST/PUT） | 执行前 setup 链自动创建 + capture 变量注入 + teardown 删除，资源名带 `autotest_<runid>_` 前缀 | **零** |
| **L2 资产池引用** | 创建代价高或不可创建（真实设备、模拟器预置资源、共享资源），但可长期复用 | 从 `environment.yaml` 池里按语义匹配（类型/厂商/型号/来源），注入实例 ID | 一次登记，长期复用 |
| **L3 用户清单** | 接口造不出、池里也没有（license 文件、特殊账号、外部依赖端点） | 聚合进 `data-manifest.yaml` 填空，用户一次填完 | 每轮仅新增项 |

判定不唯一时（例如 router 既可自建也可用池里的）：**默认 L1**——自建的数据可预期、可清理、不污染共享环境；池资源留给真正造不出的场景（真实设备等）。用户可在 manifest 里对单个 need 强制 `prefer: pool` 覆盖默认。

### 4.3 `needs` 声明（case schema 扩展）

在 `assets/case-schema.json` 的用例对象上新增可选字段：

```json
{
  "id": "GET /v1/devices/{deviceId}__sync_status",
  "class": "happy_path",
  "needs": [
    {
      "resource": "device",
      "attrs": { "type": "router", "vendor": "any" },
      "state": "managed",
      "exclusive": true,
      "purpose": "被查询的目标资源"
    }
  ],
  "request": { "method": "GET", "path": "/v1/devices/{{device_1.id}}/sync-status" },
  "assertions": [ ... ]
}
```

字段语义：

- `resource`：资源类别（device、license、topo、账号……），与 manifest/池里的 key 对应；
- `attrs`：语义属性过滤条件，支持 `any`/具体值/枚举多选；
- `state`：所需前置状态（managed / unmanaged / synced……），L1 时展开为创建后的状态迁移步骤；
- `exclusive`：是否独占该资源（写操作用例应置 true，避免用例间相互踩）；
- 占位符 `{{device_1.id}}`：resolver 把解析出的实例注入到 request 里，命名规则 `{{<resource>_<序号>.<字段>}}`。

**v0.2 的 setup/teardown 字段保持兼容**：显式写了 setup 的用例跳过 needs 解析（视为用户自己管数据）。needs 是给"声明式"用户的，setup 是给"命令式"用户的逃生门。

### 4.4 聚合器与 `data-manifest.yaml`

新增脚本 `scripts/aggregate_needs.py`：扫描 cases.json 全部 needs → 按 (resource, attrs, state) 归并去重 → 逐项跑 4.2 的分流判定 → 生成/更新 manifest 骨架：

```yaml
# data-manifest.yaml —— 聚合器生成骨架，<FILL> 为用户输入区
meta:
  run_id: autotest_20261009_a3f
  cases_total: 142
  needs_deduped: 9          # 142 条用例去重后只有 9 项需求
  delta_of_round: 2         # 本轮新增项数

resources:
  # ── L1 自动自建（自动填好，用户无需动）──
  - need: device.router[any, managed]
    provisioning: auto
    count: 3
    via: POST /v1/devices   # 聚合器从 endpoints.json 找到的创建接口
    template: templates/device-router.json
    teardown: DELETE /v1/devices/{id}

  # ── L2 资产池（用户登记一次，跨轮次/跨项目复用）──
  - need: device.otn[vendor-a, any]
    provisioning: pool
    pool_ref: environment.yaml#elements.otn
    status: matched         # 池里已有 2 个匹配实例
    consumed_by: [TC-031, TC-047, TC-058]

  # ── L3 用户填空（接口造不出、池里没有）──
  - need: license.file
    provisioning: user
    value: <FILL: license 文件路径>
    consumed_by: [TC-012, TC-013]

values:                     # 字段级领域值字典（EvoMaster 式）
  device.model: <FILL: 常见型号枚举，如 [Model-A100, Model-B200]>
  device.version: <FILL: [v2.1.0]>

credentials:                # 只声明角色；token 永远走环境变量
  roles: [read-only, admin]
```

设计要点：

- **骨架自动生成、填空式交互**：L1 段落全自动填好；L2 自动匹配并标注命中情况；只有 `<FILL>` 是用户的活。用户视角是"填一张 9 行的表"，不是"给 142 条用例配数据"；
- **`consumed_by` 反向索引**：用户能看到每个数据项影响哪些用例——某项填不了时，明确知道会跳过哪几条（标记 `skipped_missing_data`，报告里显式列出，不许静默消失）；
- **manifest 即回归资产**：填好的 manifest 存在 workspace 里，下轮回归直接复用，零交互。

### 4.5 环境资产池 `environment.yaml`

用户长期维护（一次提供，多次使用），聚合器只读不写：

```yaml
elements:
  router:
    - id: "dev-router-0001"
      vendor: vendor-a
      model: Model-A100
      source: simulator        # simulator | real
      managed: true
  otn:
    - id: "dev-otn-0002"
      vendor: vendor-a
      source: real
      managed: true
      notes: 实验室真机，勿执行写操作
      writable: false          # 池资源默认只读；写操作用例若 exclusive 则改走 L1

simulator:
  base_url: http://sim.internal:8080
  can_provision: [router, switch]     # 模拟器能起的类型
  cannot: [otn-real, microwave]

constraints:
  shared_env: false          # true 时所有写操作降级保守模式
```

**池资源默认只读**是铁律级约束：真实设备/共享资产上跑写操作用例，必须 `writable: true` 显式声明，否则 resolver 把该 need 重新分流到 L1 自建。这条防止闭环在别人的资源上留脏数据——和 v0.2"共享环境归灰灯"的保守哲学一脉相承。

### 4.6 解析器与 runtime binding

新增脚本 `scripts/resolve_data.py`：

1. 读 manifest（已填）+ environment.yaml + cases.json；
2. 对每个 need 生成绑定：L1 → 生成"创建链"描述（不立即执行，交给 run_cases 执行期）；L2 → 从池匹配实例，注入 `id`；L3 → 取用户值；
3. 校验完整性：任何 `needs` 未解析 → 相关用例标 `skipped_missing_data`，**不许带空占位符进执行器**；
4. 产出 `cases.resolved.json`（执行器唯一输入）+ `bindings.json`（审计用：哪条用例用了哪个资源实例）。

### 4.7 增量 diff：迭代不重问

闭环第 2、3 轮修复用例后重跑 `aggregate_needs.py --diff`：

- 已存在的 need（同 resource+attrs+state）：不动，沿用已解析绑定；
- 新增 need：追加到 manifest 末尾，标 `delta_of_round: N`，聚合器输出里只高亮新增段；
- 消失的 need：标记 `orphaned`，绑定释放，L1 资源下轮不再创建。

用户交互成本：第 1 轮填一次（个位数填空项），第 2、3 轮通常为零或 1-2 项。

### 4.8 通用设备场景走查（示例）

需求："测设备管理模块，覆盖 router / switch / OTN 三种类型"：

| 用例需求 | 分流结果 | 用户动作 |
|---|---|---|
| router × 3（增删改查、状态迁移用例） | L1：`POST /v1/devices` 可创建 | 无 |
| switch × 2（拓扑查询用例） | L1：模拟器 `can_provision` 含 switch | 无 |
| OTN 真机 × 1（性能数据上报用例） | L2：池里 `elements.otn` 命中 | 登记一次（以后复用） |
| license 文件（激活类用例） | L3：接口造不出 | manifest 填 1 个路径 |
| 型号枚举（边界用例取值） | L3 values： | manifest 填 1 行枚举 |

结果：142 条用例 → **用户一共填 3 个空 + 登记一次资产池**。这就是"聚合一次性提供"在该设计下的真实形态。

## 5. 工作流变更汇总

| 步骤 | 变更 |
|---|---|
| Step 3 用例生成 | 取值优先级改为 spec example > enum > values 字典 > 构造；生成 needs 声明；新增 `property` 用例类别 |
| **Step 3.5（新增）** | `aggregate_needs.py` → 三层分流 → manifest 生成/增量 diff →（用户填空）→ `resolve_data.py` → cases.resolved.json |
| Step 4 执行 | 执行前跑 L1 创建链（capture 注入），执行后跑 teardown；读 cases.resolved.json；跳过 `skipped_missing_data` 用例并在结果中显式记录 |
| Step 5/6 归因 | 新增归因信号："数据未解析"类跳过单列一节，不算红灯不算覆盖 |
| Step 9 报告 | 新增"数据供给报告"：各层命中统计、manifest 填写情况、池资源使用记录、跳过清单及原因 |
| 输入契约 | 新增可选输入：`environment.yaml` 路径（无则 L2 层禁用，全部下沉 L1/L3） |

新增铁律候选（并入 SKILL.md 铁律列表）：

> **铁律 6：`NO RAW DATA IN CASES`** —— 用例文件禁止出现具体环境数据（实例 ID、真实 IP、路径）；数据只能经 needs → manifest/池 → resolved 注入。token 依旧只走环境变量。

## 7. 风险与边界

1. **创建接口本身有 bug**（L1 链失败）：归为环境噪声（灰灯）处理——创建链失败时该 need 关联用例整组挂起并报障，不逐条判红；
2. **需求语义归并过度**（两个用例看似同 need 实则要求不同 state）：`state` 参与归并键，且 resolver 绑定后执行失败会提示"该绑定可能不满足用例真实意图"，归黄灯走人工；
3. **真实设备误写**：双层防护（池默认只读 + exclusive 强制 L1）已覆盖，报告中再单列"池资源写操作审计"；
4. **多用户并行跑闭环**：L1 前缀天然隔离；池资源加 `leased_by`（运行期软锁，run_id 标记，崩溃残留可清理）——v0.3 先做软锁，够用。
